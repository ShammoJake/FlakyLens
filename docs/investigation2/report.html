What Context Is Worth

The class around a test carries category signal the test body does not. Measured with a fixed token lexicon on 80 flaky tests, it is worth 35 accuracy points to a classifier that was never trained. All of it is order dependency.

The measurement

A lexicon of 36 regex token families, six to eight per category, applied identically to the test body and to the class around it.

Investigation 1 read 27 Hadoop tests by hand and found the deciding evidence outside the body in all 17 the model got wrong. That was a judgement call on a small sample. This step tests the same claim mechanically, on 80 tests across five projects, with a lexicon written from the standard flaky-test taxonomy before any of these sources were opened.

Because the lexicon is fixed and applied the same way everywhere, a difference between the body score and the context score is a property of the code, not of the lexicon. Scoring counts distinct families present rather than raw occurrences, since context is far longer than a body and raw counts would reward length instead of signal.

Two things fall out. Adding class fields and fixture bodies is the configuration that pays, and it pays reliably. Adding everything else on top of that makes it worse. The difference between those two rows is the sibling test bodies.

All of the gain is one category

Recall per category, body only against body plus full context.

Read this as "context helps order dependency", not "context helps". Nothing here shows a gain for async wait, concurrency, time or unordered collections. On this sample the first two get worse, because context tokens outvote the body's own async vocabulary when everything is poured into one bag.

That failure mode is informative rather than fatal. It says the context slices should enter the model as separate feature groups, not concatenated into the body's token stream. The plan already separates them; this is the measurement that says it must.

Where the code comes from

The body is FlakyLens's own copy. Everything else is pulled from GitHub at the pinned commit. The two do not always agree.

The benchmark ships each test's body in its full_code column, and a separate file pins one or more commits per repository. Context has no second source, so it has to come from a clone. Comparing the benchmark's body against the body at the pinned commit shows the pin is often not the version the benchmark used.

So the body slice is taken from the benchmark, which is what the model consumed and what the label describes. Context is taken from the clone, because there is nowhere else to get it. Where a class was restructured between the two, the context is approximate, and that is a limitation of the measurement rather than a choice.

TestDFSIO.testRead shows why this matters. What FlakyLens saw:

long tStart = System.currentTimeMillis();
bench.readTest(fs);
long execTime = System.currentTimeMillis() - tStart;
bench.analyzeResult(fs, TestType.TEST_TYPE_READ, execTime);

What the pinned commit holds:

long execTime = bench.readTest(fs);
bench.analyzeResult(fs, TestType.TEST_TYPE_READ, execTime);

The body the model actually consumed contains a wall-clock idiom twice, which is exactly why it answers "time". Scoring against the pinned commit's body would have hidden that. With the correct body the proxy scores time=1 and order dependency=1 on the body alone, a tie; adding fields and fixtures makes it order dependency=5 and the answer flips to correct.

One test, end to end

The three TestPathData cases are the clearest illustration of both the gain and the failure mode. Here is the pipeline on one of them.

TestPathData.testCwdContents has ground truth order dependency and was predicted unordered collections. The class is split into slices, the lexicon is matched against each, and the score is the number of distinct families that fire.

The body contains exactly one signal, a call to getDirectoryContents, which is a genuine unordered-collections cue and is why the model answers as it does. The fixture holds four order-dependency families and never reaches the model. The helper is the cautionary half: sortedString builds its result with a StringBuilder, which fires an unordered-collections family and pushes back toward the wrong answer. Investigation 1 read the same helper by hand and drew the opposite conclusion from its Arrays.sort call, which the lexicon has no family for.

That gap is the honest limit of this method. A regex lexicon sees that a helper touches sequences. It cannot see that the helper sorts, which is what actually rules out unordered-collection flakiness. A model reading the helper source could.

This overturns one earlier claim. Siblings are not noise. On their own they are worth +0.068 macro-F1 with an interval excluding zero, and they give the best binary order-dependency AUC of any single slice, 0.795 against 0.662 for the body alone. What hurt was pooling four slices into one group of five features, not the siblings themselves.

Siblings are redundant rather than harmful. Added on top of fields and fixtures the score moves from +0.096 to +0.091, a wash. They carry much the same order-dependency evidence the class fixture already carries, so little is left to add.

Fixtures are the strongest single slice, not fields. Fixtures alone reach 50.0% argmax accuracy and 61% order-dependency recall; fields alone reach 37.5% and 43%. Fields still show the largest coverage asymmetry between misses and hits, so the two measure different things and both are worth keeping.

Callees are the only slice that fails outright. +0.012 with an interval crossing zero and a binary AUC of 0.568, close to chance. The negative result for depth-1 callees survives unchanged.

More slices is not better at this sample size. All six kept separate is 30 features on 80 examples and scores +0.049, well below the 15-feature configuration. That is a dimensionality effect, not a statement about signal.

Production callees at depth 1

Investigation 1's fourth extraction target, now implemented. It does not help, and why it does not is the useful part.

Calls are resolved by receiver type, not by name. Local declarations and class fields give a variable-to-type map, so cache.put(...) after PeerCache cache = new PeerCache(...) resolves to PeerCache.put rather than to every put in the repository. A call is kept only when its receiver type is a class under the project's own main source tree, which drops JUnit, Mockito and the JDK without a deny list. Seventy-eight of the 80 tests resolve at least one callee, median two.

 Every measure moves the wrong way.

The signal is present; the scoring cannot use it. The callees slice carries the true category for 33% of the tests the model gets wrong against 5% of the ones it gets right. That 28-point gap is the second largest of any slice, behind only fields. Concurrency is the one category whose recall improves, 10% to 20%, exactly as investigation 1 predicted, since concurrency evidence lives in production code.

Two reasons it fails as a bag, and both are fixable.

Depth 1 is the wrong depth. TestPeerCache was investigation 1's flagship production-code case. At depth 1 it resolves PeerCache.put, size and close, which between them contain a single synchronized keyword. The background daemon and the Thread.sleep(expiryPeriod) loop live in startExpiryDaemon and run, which put calls. They sit at depth 2. The plan document specifies depth 2 by default, and this is the measurement that says why.

Callee bodies are long and generic. A production method drags in vocabulary from every category, so pouring it into one bag dilutes the body's own signal. The same failure mode as sibling tests, one level worse.

The conclusion is not to drop the slice. It is to expand to depth 2, keep it a separate feature group rather than concatenating it, and expect the gain in concurrency rather than order dependency, which is a class-level property already served by fields and fixtures.

Statistics and tooling

scikit-learn 1.9.0 and scipy 1.18.1, both pinned in the project's requirements. A numpy implementation is kept as a cross-check.

What this changes about the extraction plan

Investigation 1 ranked extraction targets by how many misses they reach. This adds what each is worth, and one correction.

  1. Static fields and fixtures pay first and pay mostThey deliver the entire measured gain on their own, and they are the cheapest thing in the plan to extract. No symbol resolution, no call graph, no build.
  2. Keep the slices as separate feature groupsConcatenating everything into one token stream costs accuracy on async wait and concurrency. The ordering from investigation 1 stands; the packaging is what changes.
  3. Sibling tests need a targeted feature, not their textThey lift the binary order-dependency AUC from 0.66 to 0.81 but dilute the five-way task. The feature that matters is which siblings write the static fields this test reads, not the sibling source.

Caveats

A lexicon is not an encoder. A 36-family regex bag is a floor. It shows the signal is present and machine-readable in the context slices. It does not predict what a fine-tuned transformer would gain, and it should not be quoted as an expected improvement. The sortedString case above shows what it misses: the lexicon sees a sequence operation where a reader sees a sort.

The class distribution is badly skewed. Order dependency is 46 of 80, unordered collections is 2, time is 4. Macro-F1 over five classes at those counts is unstable. The binary order-dependency result is the more trustworthy summary of the same effect.

The proxy beating the shipped model is not a result. These 80 tests over-represent the projects where localisation succeeded, and they are order-dependency heavy. The comparison is not like for like and should not appear in a paper as one.

Localisation loses a third of the sample. Any conclusion here is conditioned on tests whose class could be found, which may not be a random subset.
